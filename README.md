# 实验室测试任务管理 Demo V1 规范

## 1. 项目概述

本项目是一个用于练习 Vibe Coding 的实验室测试任务管理 Demo。

V1 只实现以下核心功能：

1. 创建测试任务
2. 查看测试任务
3. 修改测试任务状态
4. 删除测试任务

第一版技术栈：

- 前端：HTML、CSS、JavaScript
- 后端：Python、FastAPI
- 数据库：SQLite

默认约定：

- 状态包括：`待开始`、`进行中`、`已完成`
- 除备注外，其余业务字段必填
- V1 只允许修改任务状态，不修改其他任务字段

## 2. 项目架构

采用前后端分层的单体架构：

```text
浏览器
  │
  ├── 加载 HTML / CSS / JavaScript
  │
  └── 通过 Fetch 调用 REST API
             │
             ▼
         FastAPI 后端
             │
             ▼
         SQLite 数据库
```

FastAPI 同时负责：

- 提供前端静态文件
- 提供以 `/api` 开头的 REST API

后端按职责划分为三层：

- API 层：接收请求并返回响应
- Service 层：处理状态变更、时间校验等业务规则
- Database 层：读写 SQLite

V1 不拆分为微服务，也不引入复杂的领域层或仓储抽象。

## 4. 数据库设计

V1 只使用一张表：`test_tasks`。

| 业务字段 | 数据库字段名 | SQLite 类型 | 规则 |
|---|---|---|---|
| id | `id` | INTEGER | 主键、自增 |
| 测试项目 | `test_item` | TEXT | 必填、不能为空 |
| 测试标准 | `test_standard` | TEXT | 必填、不能为空 |
| 样机数量 | `sample_quantity` | INTEGER | 必填、必须大于 0 |
| 测试负责人 | `owner` | TEXT | 必填、不能为空 |
| 测试设备 | `equipment` | TEXT | 必填、不能为空 |
| 开始时间 | `start_time` | TEXT | 必填，使用 ISO 8601 格式 |
| 预计完成时间 | `expected_end_time` | TEXT | 必填，不早于开始时间 |
| 状态 | `status` | TEXT | 必填，默认 `待开始` |
| 备注 | `notes` | TEXT | 可选 |

时间格式示例：

```text
2026-09-01T09:30:00
```

数据规则：

- `sample_quantity` 必须是正整数。
- `expected_end_time` 不能早于 `start_time`。
- `status` 只能是 `待开始`、`进行中`、`已完成`。
- 后端校验时处理文本前后空格。
- `id` 由数据库生成，前端不能传入。
- 备注为空时，在项目内统一存为空字符串或空值。

V1 数据量较小，不额外设计索引；主键索引由 SQLite 自动提供。

## 5. API 设计

API 前缀统一为 `/api`，资源路径为 `/api/tasks`。

| 功能 | 方法 | 路径 | 成功状态码 |
|---|---|---|---:|
| 创建任务 | POST | `/api/tasks` | 201 |
| 查看任务列表 | GET | `/api/tasks` | 200 |
| 查看单个任务 | GET | `/api/tasks/{id}` | 200 |
| 修改任务状态 | PATCH | `/api/tasks/{id}/status` | 200 |
| 删除任务 | DELETE | `/api/tasks/{id}` | 204 |

### 5.1 创建任务

请求包含除 `id` 之外的任务字段。`status` 可以不传，未传时由后端设置为 `待开始`。

成功后返回完整任务对象，包括数据库生成的 `id`。

### 5.2 查看任务列表

返回任务数组，建议按 `id` 倒序排列，使新创建的任务显示在最上方。

V1 不加入分页、搜索和筛选参数。

### 5.3 查看单个任务

任务存在时返回完整任务对象；任务不存在时返回 HTTP `404` 和清晰的错误信息。

### 5.4 修改任务状态

请求只包含新的 `status`，不能通过此接口修改其他字段。

后端校验：

- 任务是否存在
- 新状态是否合法

V1 允许三个状态之间直接切换，不实现复杂的状态流转限制。

### 5.5 删除任务

采用物理删除：

- 前端删除前显示确认提示
- 删除成功返回 `204`
- 任务不存在返回 `404`

### 5.6 错误规则

| 场景 | 状态码 |
|---|---:|
| 请求字段缺失或格式错误 | 422 |
| 业务规则不满足 | 400 或 422，项目内保持统一 |
| 任务不存在 | 404 |
| 后端未预期错误 | 500 |

## 6. 前后端交互方式

前端使用浏览器原生 `fetch` 调用 API，数据格式统一为 JSON。

页面包含：

- 页面标题
- 创建任务表单
- 任务列表
- 每个任务的状态选择控件
- 每个任务的删除按钮
- 加载中、空列表和错误提示状态

主要交互流程：

1. 页面加载时调用 `GET /api/tasks`。
2. 用户提交表单时调用 `POST /api/tasks`。
3. 创建成功后清空表单并刷新列表。
4. 用户修改状态时调用 `PATCH /api/tasks/{id}/status`。
5. 用户删除任务时先确认，再调用 `DELETE /api/tasks/{id}`。
6. 请求失败时在页面显示可理解的错误信息。

前端可以进行基本校验，例如必填和数量范围；后端必须再次校验所有规则。

## 7. 开发顺序

1. 确认状态值、必填字段和时间规则。
2. 创建目录结构和 Python 运行环境。
3. 建立数据库连接并初始化 `test_tasks` 表。
4. 实现创建任务 API，并通过 FastAPI 文档页验证。
5. 实现任务列表和单个任务查询 API。
6. 实现状态修改 API。
7. 实现删除 API。
8. 为后端 API 补充自动化测试。
9. 创建前端页面、表单和任务列表。
10. 接入创建、查询、状态修改和删除接口。
11. 处理加载、空列表、错误提示和删除确认。
12. 完成完整业务流程验收。
13. 编写 README，记录安装和启动步骤。

阶段验收标准：

- 后端阶段：在 FastAPI `/docs` 页面可以完成全部接口操作。
- 前端阶段：只通过页面即可完成完整业务流程。
- 最终阶段：重启服务后，SQLite 中的数据仍然存在。

## 8. 测试方案

### 8.1 后端自动化测试

使用 `pytest` 和 FastAPI `TestClient`。测试使用独立的临时 SQLite 数据库，不操作开发数据库。

至少覆盖：

- 创建合法任务成功
- 创建后自动生成 `id`
- 未传状态时默认为 `待开始`
- 样机数量为 0 或负数时失败
- 必填字段缺失时失败
- 预计完成时间早于开始时间时失败
- 查询空任务列表成功
- 创建后可以在列表中查到任务
- 查询不存在的任务返回 `404`
- 修改合法状态成功
- 修改为非法状态失败
- 修改不存在任务返回 `404`
- 删除任务成功
- 删除后无法再次查询
- 删除不存在任务返回 `404`

### 8.2 前端手工测试

- 表单必填提示正常
- 时间输入和样机数量限制正常
- 创建成功后列表立即更新
- 刷新页面后数据仍存在
- 状态修改成功并被保存
- 取消删除确认时任务保留
- 确认删除后任务消失
- 后端未启动时显示可理解的错误
- 空列表显示正确
- 窄屏下表单和任务列表仍可用

### 8.3 最终验收场景

1. 创建一条“高温存储测试”任务。
2. 在任务列表中找到该任务。
3. 将状态从 `待开始` 改为 `进行中`。
4. 刷新页面，确认状态仍为 `进行中`。
5. 将状态改为 `已完成`。
6. 删除该任务。
7. 刷新页面，确认任务没有恢复。

## 9. V1 明确不做的内容

为控制练习范围，V1 不实现：

- 用户注册、登录、权限和角色
- 修改除状态以外的任务字段
- 项目、负责人、设备的独立管理
- 设备占用和时间冲突检测
- 搜索、筛选、可配置排序和分页
- 文件、图片和测试报告附件
- 消息通知、邮件和到期提醒
- 操作日志和状态历史
- 批量创建、批量删除和 Excel 导入导出
- 仪表盘、统计图表和数据分析
- 软删除和回收站
- 多语言和深色模式
- WebSocket 实时更新
- 前端框架
- Docker、云部署和 CI/CD
- 微服务、缓存和异步任务队列
- 数据库迁移工具
- 复杂的状态流转和审批规则
- 为未来需求预留抽象接口

## 10. V1 完成标准

当以下条件全部满足时，认为 V1 完成：

- 用户可以通过页面创建测试任务。
- 用户可以查看任务列表和任务详情。
- 用户可以修改任务状态。
- 用户可以删除任务。
- 非法输入会被后端拒绝。
- 任务数据会保存到 SQLite。
- 服务重启后数据不会丢失。
- 后端自动化测试通过。
- 核心验收场景可以完整执行。
